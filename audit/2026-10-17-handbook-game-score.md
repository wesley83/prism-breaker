### Prioritized findings

**HS-01: Save failure must govern subsequent actions (high).** Source-confirmed weakness, runtime reproduction not executed here. `public/editor.js:38` catches draft write failures and displays a warning but returns no result to callers; `commit` can replace that warning with a successful change message. The world selector at line 29 navigates unconditionally. Failed storage followed by navigation can lose the unsaved working copy. `public/app.js:24` silently catches checkpoint write errors; `persist` at line 71 receives no success/failure signal, while the pause description at line 170 says the checkpoint is saved. Follow handbook Sections 4-5: use explicit write outcomes, keep the working copy, and gate destructive/replacing transitions behind retry/export/deliberate discard. Verify denied storage/quota followed by world switching, reload/import, preview return and save-and-leave through ordinary controls.

**HS-02: The editor's editable authority is a JavaScript object (high for full document-first adherence).** Source-confirmed mismatch with the newer handbook Sections 3-4. `public/editor.js:11` owns `world`; change commands mutate it and the DOM is reconstructed/decorated from those values. Authored HTML and a DOM view do not establish a DOM-backed editable working model. No concrete workload exception explaining why this document editor cannot suitably use the preferred DOM authority was found. Prefer a declared semantic working root with typed accessors and commands; derive preview arrays and export from it. Preserve selection and UI state outside that root. Test live form values, identity-preserving moves, no save for selection-only changes, cancellation, unknown fields and delayed-save dirty state. A parsed model can meet the handbook only with its concrete justified exception and complete conversion/recovery contract; framework convenience is insufficient.

**HS-03: Gameplay input lacks complete pointer ownership (high).** Source-confirmed weakness; no new gesture reproduction. `public/app.js:190,199-202` uses one global dragging flag. It does not retain an owning pointer ID, filter accepted mouse buttons, handle lost pointer capture, or cancel dragging in ordinary modal/blur/resize transitions. A second contact can move the paddle or release the flag for the first contact. Move handling also lacks the modal check used on pointerdown. Section 10 calls for explicit contact ownership, allowed buttons and idempotent cancellation. Test two contacts, capture loss, pause/resume, orientation changes and mouse-button chords with ordinary input paths. A single-contact paddle scheme may reject additional contacts deliberately; it does not need a gamepad or two-thumb UI.

**HS-04: Duplicate score acknowledgement is not payload-bound (medium).** Source-confirmed weakness. `public/app.js:209-213` handles a 422 by finding the existing run key and reporting acceptance without comparing alias, score, mode, day, duration, progress or rules revision. This can acknowledge a different payload under that key. Server uniqueness is valuable and prevents ordinary duplicate inserts, but Section 9 requires matching accepted content before acknowledging an ambiguous retry. Compare canonical fields and retain a conflict when they differ. `public/offline.js:78` also has deterministic retry delays without jitter; no Retry-After handling was found in the score sender. Add bounded jitter and supported retry-header handling without changing the selected casual-board trust model. Review lease/payload/expiry interleavings and final exact-tie ordering separately.

**HS-05: Checkpoint restore is not fully staged (medium).** Source-confirmed structure and evidence gap, not a reproduced late-failure bug. `public/engine.js:194-201` validates first, then calls `this.start` on the active instance before all cloning, portal restoration and behavior configuration completes. Section 5 asks for a coherent prepared candidate committed at one boundary and a failure in the final preparation step. Stage the complete candidate and retain the previous usable run if late validation/preparation fails. Existing malformed/ruleset/pinned-definition tests are useful but do not establish that final failure invariant.
